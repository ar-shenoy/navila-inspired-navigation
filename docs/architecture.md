# System Architecture

This document describes the architecture used in this repository, which is directly inspired by NaVILA.

---

## High-Level Overview

```text
Language Instruction + RGB Observation
                │
                ▼
┌─────────────────────────────────────┐
│      High-Level VLA / Planner       │
│  (Vision + Language → Mid-level     │
│   spatial command)                  │
└─────────────────────────────────────┘
                │
                │  "move forward 0.75m"
                │  "turn left 30 deg"
                ▼
┌─────────────────────────────────────┐
│     Low-Level Controller            │
│  (Executes mid-level command +      │
│   basic obstacle avoidance)         │
└─────────────────────────────────────┘
                │
                ▼
          Robot Motion
```

---

## 1. High-Level Module (`src/high_level/`)

**Responsibility:**  
Convert a natural language instruction and current visual observation into a **mid-level spatial command**.

Examples of mid-level commands:
- `move_forward(distance=0.75)`
- `turn_left(angle=30)`
- `turn_right(angle=45)`
- `stop()`

In a full NaVILA-style system this would be a large Vision-Language Model.  
In this repository we implement a simplified but clear version that can run on Kaggle T4.

---

## 2. Low-Level Module (`src/low_level/`)

**Responsibility:**  
Take the mid-level command and turn it into actual movement, while performing basic safety checks.

In NaVILA this is a sophisticated RL locomotion policy.  
Here we use a simple kinematic / velocity controller so the idea remains clear and runnable.

---

## 3. Interface Between Levels

The interface is deliberately kept as **language-like spatial commands**.  
This has several advantages:

- Easy to understand and debug
- Can be generated by different high-level models
- Can be executed by different low-level controllers / robots
- Matches the design philosophy of NaVILA

---

## 4. Design Principles Followed

1. **Hierarchy over end-to-end** – Do not predict joint actions directly from the VLA.
2. **Clear separation of concerns** – High-level reasons about *what* to do, low-level handles *how* to do it safely.
3. **Runnable on limited hardware** – Focus on the high-level reasoning part that can run on T4 / consumer GPUs.
4. **Documentation first** – Make the ideas easy for a reviewer (or Fauzy) to understand quickly.
